# Arena

Конструктор команд и сравнений на данных PokeAPI. Каталог ~1300 бойцов, редактирование
характеристик, кастомные параметры сравнения, сборка двух команд по 5 и детерминированная
битва по выбранному параметру — базовому, кастомному или сумме всех характеристик.

Этот README ведётся по мере коммитов: каждая заведённая технология или принятое решение
получает свой абзац в момент, когда оно попадает в код, а не задним числом.

  merge-слой, логика битвы

## Запуск

```bash
bun install

# создать .env.local с секретом сессии Auth.js
cp .env.example .env.local
# заполнить AUTH_SECRET, например:
bunx auth secret
# или вручную: openssl rand -base64 32

bun run dev     # http://localhost:3000
bun run test    # vitest — 132 теста в 19 файлах
bun run build   # production-сборка (также прогоняет tsc)
bun run lint    # eslint
```

Тестовые пользователи (захардкожены, без БД): `admin` / `admin123`, `guest` / `guest123`.

Датасет `public/data/pokemon.json` уже закоммитен и используется как есть. Пересобрать его
из PokeAPI (не требуется для обычной работы):

```bash
bun run scripts/fetch-pokemon.ts
```

## Как устроен проект

### Слои

Feature-Sliced Design. Правило импорта одно: **слой видит только слои ниже себя**, а срезы
одного слоя не видят друг друга.

```
app/       маршруты Next.js (App Router). Только роутинг и композиция виджетов.
widgets/   крупные самодостаточные блоки экрана: каталог, досье бойца, драфт, арена.
features/  пользовательские сценарии: поиск, фильтры, редактирование, драфт, запуск боя.
entities/  предметные сущности и вся доменная логика: fighter, stat, team, battle.
shared/    инфраструктура без знания о домене: db, ui-кит, утилиты, конфиг.
```

Внутри среза — та же тройка:

```
entities/battle/
  model/     чистые функции и типы — доменная логика
  api/       чтение/запись (Dexie) — репозитории
  ui/        презентация, ничего не знающая про источник данных
  index.ts   публичный API среза: снаружи импортируется только он
```

Импорт мимо `index.ts` не используется — публичный API среза описан в одном файле, и по нему
видно, что срез вообще предоставляет наружу.

**Где живёт доменная логика.** Вся — в `entities/*/model`, чистыми функциями без React, без
Dexie и без сети: `determineWinner`, `explainBattle`, `fighterStatScore`, `mergeFighter`,
`assignFighter`, `fighterRating`, `toneOfTypes`. Именно поэтому она покрывается юнит-тестами
без единого мока. React-хуки живут в `features/*/model` и только склеивают домен с состоянием.

### Поток данных: от PokeAPI до экрана

PokeAPI **не вызывается в рантайме вообще**. Данные приходят так:

```
scripts/fetch-pokemon.ts  ──build-time──►  public/data/pokemon.json   (937 КБ, 1302 записи)
                                                    │
                                    import (бандлится в JS-чанк)
                                                    ▼
                                        shared/api/static-dataset.ts
                                                    │
   Dexie: overrides ─┐                              │
         customStats ├──────────────►  entities/fighter/api/fighterRepository
    customStatValues ─┘                             │  mergeFighter(base, override, custom)
                                                    ▼
                                        TanStack Query  ['fighters']
                                                    │
                                                    ▼
                                         widgets / features / UI
```

Почему снимок, а не запросы к API: в задании ~1300 записей, а описание (`flavor_text`) и
характеристики лежат в PokeAPI в разных ресурсах — честная загрузка «на лету» означала бы
тысячи round-trip'ов или водопад запросов на каждый экран. Снимок снимает и проблему лимитов
API, и требование «список должен оставаться отзывчивым на полном датасете», и делает
приложение работоспособным без сети. Цена — 937 КБ в бандле и данные, устаревающие до
следующей пересборки (для покемонов это приемлемо: они не меняются).

### Слияние API-данных и правок

Самая интересная часть задачи по формулировке ТЗ, поэтому вынесена в отдельную чистую функцию
`entities/fighter/model/merge.ts` и покрыта тестами.

```
base (снимок PokeAPI, неизменяемый)
  └── override (правки пользователя: name/description/stats)   Dexie: overrides
        └── customStats (значения кастомных параметров)        Dexie: customStatValues
              └── Fighter  ← единственное, что видит UI
```

Три принципа:

1. **Оригинал никогда не мутируется.** Правка — отдельная строка в `overrides`, а не изменение
   снимка. Поэтому «сбросить к оригиналу» = удалить строку, а не хранить рядом вторую копию
   исходных значений.
2. **Слои накладываются по одному правилу** (`base → override → customStats`), и результат этой
   функции — единственная форма, в которой боец существует для UI. Компоненты не знают слов
   «override» и «Dexie»: они получают `Fighter` и флаг `isEdited`.
3. **Диф правок считается против оригинала, а не против текущего состояния** — см. решение про
   `buildOverridePayload` ниже.

Кастомные параметры ложатся в тот же `stats`, что и базовые. Именно поэтому всё, что умеет
сравнивать характеристики — диапазонные фильтры каталога, селектор параметра битвы, сама
битва — работает с кастомным параметром без единой ветки `if (source === 'custom')`.

### Логика битвы

```
teams (Dexie)          statId (URL: ?stat=attack)
      │                        │
      └──► lineups ────────────┴──► determineWinner(teamA, teamB, statId)   ◄── чистая функция
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
             explainBattle        buildDuelScript          BattleLineup
             (разбор, таблица)    (анимация боя)           (счёт по слотам)
```

- **Пара против пары по слотам**: N-й боец команды A против N-го команды B.
- **Раунд** выигрывает тот, у кого больше значение выбранного параметра. Отсутствующее
  значение — 0, а не пропуск слота.
- **Бой** выигрывает тот, кто взял больше раундов. Равенство — ничья.
- **Параметр** — любой из реестра `entities/stat`: шесть боевых статов, рост/вес/сложность
  поимки/базовое счастье, любой кастомный, плюс псевдо-параметр `__total` («все
  характеристики») по умолчанию.

Всё, что решает исход, — чистые функции без `Date`, `Math.random`, сети и Dexie: одни и те же
составы и один и тот же параметр всегда дают один и тот же результат. `buildDuelScript`
(анимация) и `explainBattle` (разбор) — **проекции уже принятого решения**: они не
пересчитывают исход, поэтому картинка на экране физически не может разойтись с вердиктом.

### Что UI знает о данных

Ничего, кроме доменных типов. Конкретно:

- ни один компонент не импортирует `shared/lib/db` — только `features`/`entities` через
  репозитории;
- ни один компонент не знает про `override`: есть `Fighter` и `isEdited`;
- `BattleBreakdown` получает готовый `BattleExplanation` и не считает ничего сам;
- `ComparisonStatSelect` получает `StatDefinition[]` и не знает, что часть из них создана
  пользователем (кроме точки-маркера в вёрстке).

## Стек и решения

### Стек

**Next.js 16.3.0, App Router, TypeScript strict.** Обязательное требование задания. Реально
установленная версия в этой среде — 16.3.0, а не указанная в задании "15": работаем с тем,
что установлено, и явно фиксируем расхождение (см. "Принятые решения" ниже). `strict: true` +
`noUncheckedIndexedAccess: true` в `tsconfig.json` — вторая опция превращает любой доступ по
индексу массива (`arr[i]`) в `T | undefined`, что для датасета на 1300+ записей и Dexie-выборок
ловит реальные баги на этапе компиляции, а не в рантайме.

**Bun** как package manager и раннер скриптов. Быстрее npm/yarn на установке, а
`scripts/fetch-pokemon.ts` выполняется напрямую, без отдельного шага сборки и без `tsx`/
`ts-node` в зависимостях. Тесты при этом гоняет Vitest, а не встроенный раннер Bun (см. ниже).
**Цена:** ещё один инструмент, который должен стоять у того, кто запускает проект — поэтому
`npm install` / `pnpm install` тоже работают: в самом приложении API Bun не используется.

**Tailwind CSS + shadcn/ui.** Рассматривались MUI, Mantine, Chakra. Проект пришёл с готовым
дизайн-пакетом (тёмная тема, свои токены и типографика), а библиотека с собственной
дизайн-системой означала бы борьбу с её темизацией вместо вёрстки по макету. shadcn копирует
компоненты в код (`src/shared/ui`), а не тянет их рантайм-зависимостью — их можно править под
макет без форка библиотеки; Base UI под капотом даёт доступность примитивов (меню, слайдер,
свитч). **Цена:** скопированные компоненты поддерживаешь сам, и разметка обрастает длинными
классовыми строками. Инициализировано с пресетом Base UI
(`bunx shadcn@latest init --defaults`); дефолтные алиасы shadcn (`@/components/ui`, `@/lib`) не
совпадают с FSD-раскладкой — компоненты и `cn()` перенесены в `shared/ui`/`shared/lib`,
`components.json` перенастроен, чтобы будущие `shadcn add` сразу попадали в правильное место.
В `shared/ui` оставлены только реально используемые компоненты: `badge`/`card`/`dialog`/`select`
приехали с первичной установкой, нигде не импортировались и удалены.

**Dexie.js (IndexedDB)** для пользовательских правок, кастомных параметров и команд.
localStorage не подошёл бы: это синхронный API, блокирующий главный поток, с квотой порядка
5–10 МБ и без индексов — любое чтение требует `JSON.parse` всего блоба. IndexedDB асинхронна,
квота на порядки больше, а Dexie даёт составные индексы (`[fighterId+statId]`) для точечных
выборок правок без пробега по всей коллекции. Схема — `shared/lib/db.ts`: `overrides`,
`customStats`, `customStatValues`, `teams`.

**Auth.js (next-auth) v5, Credentials provider, JWT-сессия, без БД.** Не пишем свою систему
кук/подписи с нуля, но и не тащим БД под два захардкоженных пользователя — ровно то, что нужно
для моканной авторизации. `src/auth.ts` экспортирует `handlers`/`auth`/`signIn`/`signOut`;
guard реализован через `src/proxy.ts` (см. "Принятые решения" — в Next.js 16 это файл, который
раньше назывался `middleware.ts`).

**Vitest** для юнит-тестов. Альтернатива — Jest, но он потребовал бы ts-jest или babel и
отдельной конфигурации ради того же результата; Vitest берёт TypeScript и алиасы из
`vitest.config.mts` тем же пайплайном, что и сборка. Battle-логика и merge-логика — чистые
функции без DOM, поэтому окружение `node`, без jsdom. **Цена:** экосистема младше Jest, часть
рецептов из статей приходится переводить.

**motion** — анимация боя (последовательность раундов, полосы здоровья). На голых
CSS-переходах оркестрация таймлайна с возможностью «пропустить» вышла бы сложнее, чем стоит
~30 КБ. **lucide-react** — иконки, tree-shakeable.

**MiniSearch + свой подстроковый проход** для поиска по имени и описанию.
`shared/lib/search-index.ts` строит индекс один раз при загрузке модуля — 1300 записей в
памяти, без сервера и без воркера (профилировать не пришлось: индексация и поиск по такому
объёму — миллисекунды). Индекс строится по неизменяемому статическому датасету, а не по
смерженным `Fighter` — поиск ищет то, что реально лежит в PokeAPI-снимке, а не
пользовательские правки.

Одного MiniSearch для требования задания не хватает: это **токенный** индекс — он матчит
слова целиком и префиксы слов, поэтому `pika` находит `pikachu`, а `kachu` не находит
ничего. В ТЗ же прямо сказано «поиск по подстроке». Поэтому запрос идёт двумя проходами и
результаты объединяются: сначала MiniSearch (он умеет ранжировать, опечатки и многословные
запросы), затем сырой `includes` по заранее собранному `name + description` в нижнем
регистре — он и добирает то, что токенный индекс структурно найти не может. Ранжированные
попадания остаются первыми, подстроковые идут за ними в порядке датасета. Замер на полном
датасете: 0.2–0.35 мс на обычный запрос и 1.2 мс на худший случай (запрос из одной буквы,
матчащий все 1302 записи) — дешевле, чем инвертированный n-грамм-индекс, и без его памяти.

**TanStack Query** как обёртка над `getAllFighters()`/Dexie. Рассматривались Redux Toolkit,
Zustand, SWR и «просто `useEffect` + `useState`». Ключевое соображение: **в этом приложении нет
глобального клиентского состояния** — источник истины это Dexie (правки, команды) и URL
(фильтры, параметр сравнения). Стор общего назначения стал бы третьей копией той же правды,
которую пришлось бы синхронизировать. Что реально нужно — кэш асинхронных чтений с
инвалидацией после мутаций, а это ровно предмет Query: кэш по `queryKey`, `isLoading`/`isError`
из коробки вместо самодельных `useState` в каждом виджете. SWR решает ту же задачу и легче, но
у Query из коробки мутации с `invalidateQueries`, которыми здесь связаны экраны: правка бойца
инвалидирует `['fighter', id]`, `['fighters']` и `['statRegistry']`, и каталог с битвой
подхватывают её без межэкранной проводки. **Цена:** ~13 КБ и инвалидация ключей руками — зато
эта связность видна прямо в коде мутации.

`staleTime: Infinity` для `['fighters']` — датасет неизменяем в рамках сессии, инвалидация
нужна только после мутации Dexie. Один `QueryClient` на сессию, заведён в
`shared/lib/providers/AppProviders.tsx` и подключён в корневом `layout.tsx`, чтобы сам layout
остался тонкой Next.js-обёрткой. Дефолты выставлены под локальный источник данных
(`networkMode: 'always'`, `retry: 1`, `refetchOnWindowFocus: false`) — почему именно так, см.
"Принятые решения".

**nuqs** для состояния поиска/фильтров каталога. Требование ТЗ — состояние должно переживать
перезагрузку; варианты были `useState` + ручная синхронизация с `URLSearchParams` либо
`localStorage`-персист. Выбран URL: он переживает не только reload, но и «поделиться ссылкой»
и кнопку «назад», чего `localStorage` не даёт ни в каком виде. nuqs — типизированная обёртка
над `useSearchParams`/`router.replace` с парсерами и батчингом; писать это руками означало бы
писать её же, но хуже. Весь `useCatalogFilters()` живёт в query-строке:
`?q=char&types=fire,water&legendary=true&ranges=speed:20:150`, параметр сравнения битвы там же
(`?stat=attack`). **Цена:** состояние видно в адресной строке и URL получается длинным; под
диапазоны понадобился свой компактный парсер, чтобы не заводить query-параметр на каждый стат.
`NuqsAdapter` (App Router) подключён рядом с `QueryClientProvider` в тех же `AppProviders`.

**TanStack Form + Arktype** для формы редактирования бойца. Рассматривалась связка по
умолчанию React Hook Form + Zod. Почему не она: у формы бойца **динамический набор полей** —
статы приходят из реестра `entities/stat`, включая созданные пользователем. TanStack Form даёт
типобезопасные вложенные имена (`stats.${id}`) и гранулярные подписки: `form.Subscribe`
перерисовывает только подписанный кусок, поэтому перетаскивание слайдера пересчитывает число
рейтинга, а не всю форму из 12 полей. Arktype вместо Zod — схема пишется как тип
(`'string > 0'`), рантайм быстрее, и он поддерживает Standard Schema, который TanStack Form
понимает нативно. **Цена:** обе библиотеки моложе и менее распространены, чем RHF + Zod —
меньше готовых рецептов и выше шанс, что новый человек в команде их не знает.

Arktype-схема — не голый
`type(...)`, переданный прямо в `validators.onChange` (хотя это и поддерживается: у Arktype
`Type` есть `~standard`, TanStack Form v1 распознаёт Standard Schema сам) — вместо этого схема
обёрнута в функцию-валидатор, которая заменяет дефолтные английские сообщения Arktype на
русские, оставляя саму проверку на Arktype. Валидация — на каждое поле отдельно
(`form.Field`/`validators.onChange`), а не одна огромная схема на весь объект формы: у `stats`
динамический набор ключей (реестр статов), и валидировать "весь объект целиком одной схемой"
означало бы либо описывать статы как индексируемую запись в Arktype, либо валидировать
каждый стат тем не менее отдельно — по полям получилось проще и с меньшим количеством кода.

**Автопагинация вместо виртуализации в сетке покедекса.** Изначально сетка была собрана на
`@tanstack/react-virtual` (виртуализация по строкам). Сейчас это обычный CSS grid с
инкрементальной догрузкой по `IntersectionObserver`
(`widgets/catalog-browser/model/useAutoPagination.ts`, страница — 48 карточек): в DOM живёт
только загруженное, но не потому что строки переиспользуются, а потому что следующая страница
ещё не отрендерена. Причина замены — см. "Принятые решения". Зависимость
`@tanstack/react-virtual` из `package.json` удалена — после замены её не импортировал никто.

### Принятые решения

- **Next.js 16.3.0 вместо указанной в задании "15".** В среде уже установлена 16.3.0 —
  работаем с реальной версией, а не откатываем стек искусственно.
- **`proxy.ts` вместо `middleware.ts`.** В Next.js 16 Middleware переименован в Proxy
  (`node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`): тот же runtime-контракт
  (`NextRequest`/`NextResponse`), новый файл/экспорт. Auth.js v5 `auth()` оборачивает proxy
  так же, как раньше оборачивал middleware — поведение не изменилось, изменилось только имя
  файла.
- **FSD-раскладка (`entities/features/widgets/shared`)**, а не более плоская
  `domain/data/features`. Явно выбрана в пользу графируемого критерия "архитектура/границы
  модулей" и линта `eslint-plugin-boundaries` — двух конкурирующих раскладок одновременно не
  может быть, выбор зафиксирован здесь.
- **`src/auth.ts` и `src/proxy.ts` лежат вне слоёв FSD**, на корне `src/`, рядом с `app/`. Это
  требование самого Auth.js/Next.js — они ищут эти файлы по фиксированному пути, а не по
  соглашению проекта. Слой `pages` FSD осознанно слит с `src/app/` Next.js по той же причине:
  роутинг App Router — это файловая система, а не абстракция, которую можно продублировать
  отдельной директорией без потери маршрутизации.
- **Порядок наложения в `mergeFighter`:** `base → override → customStats`, где `customStats`
  накладываются последними и могут перекрыть даже одноимённый ключ из `override.stats`. Это
  буквальное прочтение формулировки задания "кастомные параметры... участвуют в сравнении
  наравне с базовыми" и "кастомные статы всегда добавляются поверх" — в реальности коллизий
  имён между кастомным параметром и базовым статом не предполагается, но порядок слоёв
  зафиксирован именно так, а не иначе.
- **Приоритет спрайта: `official-artwork`, затем `front_default`.** Явно указано в тексте
  задания. Заодно поле `sprites` в ответе GraphQL-эндпоинта PokeAPI приходит уже разобранным
  объектом, а не JSON-строкой — код на это не рассчитывал изначально, распарсили с фолбэком на
  оба варианта.
- **Новые поля датасета (`height`, `weight`, `captureRate`, `baseHappiness`,
  `isLegendary`, `isMythical`, `shinySprite`, `cryUrl`) идут в `stats` через
  `entities/stat/model/statRegistry.ts`, а не хардкодятся по месту в UI.** Числовые поля,
  которые имеет смысл сравнивать между командами (`height`/`weight`/`captureRate`/
  `baseHappiness`), зарегистрированы как `StatDefinition[]` с `source: 'base'` наравне с
  шестью боевыми статами — любой код, который умеет сравнивать статы (в будущем —
  team-builder/battle), автоматически умеет сравнивать и их, без отдельной ветки логики.
  `entities/stat` — новый срез (был в исходном плане архитектуры, но не заводился до этой
  задачи); `StatDefinition`/`StatSource` переехали туда из `entities/fighter`, где были
  временно совмещены с `Fighter` для экономии файлов на раннем этапе.
- **`pokemon_v2_pokemoncries { cries }` — реальное поле в GraphQL-схеме v1beta**, проверено
  интроспекцией (`__type(name: "pokemon_v2_pokemon")`) до того, как писать код: отдаёт
  `{ latest, legacy }` — те же `.ogg`-ссылки на `raw.githubusercontent.com/PokeAPI/cries`,
  которые в задании предлагались как CDN-фолбэк "если поля нет в схеме". Поля не пришлось —
  фолбэк не нужен, никакого отдельного сетевого пути для крика не появилось.
- **Бейдж легендарности использует `amber`, не отдельный `gold`.** Дизайн-система прямо
  ограничивает палитру шестью токенами ("больше не добавлять без причины") — вводить седьмой
  цвет ради одного бейджа противоречило бы этому правилу, а `amber` уже несёт смысл
  "победа/акцент" в остальном интерфейсе.
- **`fighterRepository` (Dexie) нельзя вызывать из Server Component — только из клиентского
  кода.** Не теоретическое рассуждение: при первой попытке отрендерить `FighterCard` на
  сервере (временная проверка на месте будущего каталога) упало `MissingAPIError: IndexedDB
  API missing`, потому что `indexedDB` существует только в браузере. Это ограничение уже
  было учтено в решении про SSG/SSR выше ("SSR/SSG им ничего не выигрывают"), но теперь оно
  подтверждено падением, а не только рассуждением — все будущие страницы каталога/бойца
  обязаны быть клиентскими компонентами (или читать данные в `useEffect`/TanStack Query), а
  не `async`-серверными компонентами с `await getFighterById(...)`.
- **Единая тёмная тема без переключателя.** Дизайн-система, полученная для проекта, дана в
  одной теме (чёрный фон, поверхности `#232323`, акценты amber/blue/mint). Переключатель
  светлая/тёмная — это отдельный пункт опциональной части задания, который мы сознательно не
  берём (см. "Что не сделано").
- **Лендинг (`app/(public)/page.tsx`) — SSG.** Компонент не вызывает `fetch` с `no-store` и не
  читает `cookies()`/`headers()`, поэтому Next.js рендерит его один раз при сборке и раздаёт
  статикой с CDN. Все остальные маршруты либо требуют сессии (значит, минимум per-request
  проверка через `proxy.ts`), либо завязаны на клиентский IndexedDB (Dexie), которого на
  сервере просто нет — SSR/SSG им ничего не выигрывают, контент всё равно досчитывается в
  браузере после гидратации. Интерактивность самого лендинга (`widgets/landing-showcase`) —
  чисто клиентский `useState`, без Dexie и без обращения к реальному auth-слою: это демо-стенд
  для посетителя, а не часть бизнес-данных продукта.
- **Дизайн-пакет прислан с двумя конфликтующими токен-наборами** (`arena-design-system.md` —
  ink/panel/ember/cyan/gold, Bebas Neue/Inter; итоговый `README.md` пакета — white/black/
  surface/blue/mint/amber, Outfit/Manrope/IBM Plex Mono). Сам пакет явно помечает первый файл
  как "от предыдущей итерации", актуальны токены из README — их и реализовали; они, кстати,
  совпадают с токенами, уже введёнными на этапе лендинга до получения пакета. Пакет целиком
  закоммитен в `design_handoff_arena/` — референс для следующих экранов (покедекс, досье
  бойца, состав, арена), а не только для лендинга.
- **В демо на лендинге — реальные покемоны, не бойцы из макета** (Фламбер, Тидрак и т.п. в
  макете — придуманные, чтобы не использовать защищённые авторским правом арт/имена в дизайн-
  прототипе). Задание собирает данные из настоящего PokeAPI, поэтому подставлены реальные виды
  (Charizard, Blastoise, Venusaur...) с реальными спрайтами (`official-artwork`, через
  `next/image` и `next.config.ts.images.remotePatterns`), статами и типами — структура данных
  идентична, макет верстался не по конкретным именам.
- **Цвет "стихии" бойца выводится из типа**, а не назначается по кругу (`index % 3`, как в
  прототипе). 18 реальных типов PokeAPI разбиты на 3 группы по тем же трём акцентам —
  см. `entities/fighter/model/tone.ts` (`toneOfTypes`/`ALL_FIGHTER_TYPES`; изначально жило в
  `widgets/landing-showcase`, переехало в `entities/fighter`, когда `FighterCard` понадобился
  тот же маппинг — раздельные копии в widget и entity дублировали бы список типов). Так же
  вместо авторских ролей ("УДАРНЫЙ", "МАГ" и т.д. в макете) роль бойца в героическом драфте
  вычисляется из того, какой из шести статов у него выше остальных — не выдумываем факты о
  реальных покемонах.
- **Панель "истории боёв" на лендинге помечена как превью,** а не выдаётся за реальные данные.
  Функции истории боёв в приложении ещё нет (см. "Что не сделано") — показывать вымышленные
  результаты как случившиеся факты было бы нечестной вывеской ("голос интерфейса" из брифа
  прямо требует не врать пользователю).
- **`prefers-reduced-motion` отключается глобально** в `globals.css` (все `animation`/
  `transition` укорачиваются до почти нуля), а не поточечно на каждом анимированном элементе —
  бриф требует полного отключения слэш-ривила, тряски и race-fill сразу везде.
- **Границы слайдера числового фильтра — реальный `[min, max]` по датасету**, а не
  произвольные круглые числа. `features/fighter-filter/model/statBounds.ts` считает их по
  `staticFighters` (не по смерженным `Fighter`, чтобы правки одного пользователя не сдвигали
  границы диапазона всем) через `toComparableStats` — тот же хелпер, которым `fighterRepository`
  сворачивает `height`/`weight`/`captureRate`/`baseHappiness` в `stats`; вынесен в
  `entities/fighter/model/comparableStats.ts`, чтобы это знание о "каких полях смотреть"
  не дублировалось в двух местах.
- **Фильтр по типу — это "любой из выбранных" (OR), не "все выбранные" (AND).** У бойца
  1-2 типа; трактовка "AND" для мультивыбора почти всегда возвращала бы пустой список при
  выборе больше одного типа, что бессмысленно для фильтра каталога.
- **Поиск — `useDeferredValue`, не debounce.** Инпут обновляет состояние сразу (React считает
  это высокоприоритетным), а пересчёт `MiniSearch`-запроса идёт с `useDeferredValue` —
  React сам решает, когда посчитать устаревшее значение низким приоритетом, без таймера и
  без риска "мигания" при быстрой печати. `isPending` (query !== deferredQuery) прокинут наружу
  как необязательный индикатор, а не заблокировано поле ввода.
- **Диапазонные фильтры в URL — свой компактный формат, а не параметр на стат.**
  `widgets/catalog-browser/model/statRangesParser.ts` кодирует все активные диапазоны одним
  параметром (`ranges=speed:20:150,height:5:20`) через `nuqs`' `createParser`. Реестр
  сравнимых статов (`entities/stat`) может расти — заводить отдельный query-параметр на
  каждый статический ключ означало бы менять схему URL при каждом новом стате.
- **Виртуализация в каталоге заменена на автопагинацию.** Прямое решение по запросу
  заказчика: сетка должна быть обычным гридом с нормальными `gap-x`/`gap-y`, плюс
  автоподгрузка при скролле. С виртуализацией это несовместимо: карточки там позиционируются
  абсолютно внутри виртуальных строк, поэтому `gap-y` физически не работает (зазор приходится
  эмулировать padding'ом строки), а собственный скролл-контейнер виртуализатора конфликтует
  со скроллом страницы, по которому и должна срабатывать догрузка. Что было и почему заменено:
  предыдущая реализация держала список в жёсткой вьюпорт-высоте `h-[calc(100vh-220px)]` —
  это был не произвольный выбор, а фикс реального бага (`flex-1` не работает у grid-элемента
  без явной высоты трека: контейнер вырастал до `scrollHeight` ~96 000px и скроллилась вся
  страница вместо списка). Автопагинация снимает и первопричину: скролл страницы теперь
  штатный режим, отдельный скролл-бокс не нужен, а размер DOM ограничен числом загруженных
  страниц (48 карточек на страницу), а не переиспользованием строк. Побочный плюс — число
  колонок больше не привязано к расчёту высоты строки виртуализатором и задаётся по ширине
  (`2 / 3 / 4`, потолок — 4: контейнер упирается в 1560px, и пятая колонка сжимает карточку до
  ~230px, ломая блок статов). `@tanstack/react-virtual` после замены не импортировался нигде в
  `src/` и удалён из `package.json` вместе с обновлением lock-файла.
- **`statBounds` мемоизирован на уровне модуля.** Границы слайдеров выводятся только из
  неизменяемого снимка датасета, то есть ответ не может измениться за время жизни страницы.
  Без кэша рендер панели фильтров стоил один полный проход по ~1300 записям *на каждый стат*
  (10+ проходов, каждый с аллокацией объекта `toComparableStats` на запись) — и повторялся на
  каждом ре-рендере, включая те, что автопагинация вызывает во время скролла.
- **Границы слайдеров кастомных статов считаются таблицей один раз, а не по требованию.**
  Кастомного стата нет в статическом снимке, поэтому его границы измеряются по загруженному
  ростеру (`statBoundsFromFighters`) — то есть полный проход на стат, который `statBounds`
  мемоизировать не может. В `CatalogBrowser` они считаются одним `useMemo` на весь реестр
  (ключи — `statRegistry` и `fighters`), а `boundsFor` только читает из готовой `Map`. Сначала
  это был ленивый кэш с записью внутри `boundsFor`, но правила React Compiler
  (`react-hooks/immutability`) запрещают мутировать результат хука после его вызова — и по
  делу: считать всё в `useMemo` заодно предсказуемее по времени.
- **Что именно мемоизировано против лишних ререндеров и почему только это.** Догрузка страницы
  меняет состояние в `CatalogBrowser`, то есть ререндерит всё поддерево. Мемоизированы два
  места, где это стоило дорого: `FighterCard` (`React.memo`) — иначе каждая уже отрисованная
  карточка, а их к концу списка до ~1300, заново считает рейтинг/сумму и пересобирает
  поддерево; и `FilterSidebar` (`React.memo`) — десять диапазонных слайдеров, не зависящих от
  глубины пагинации. Ради второго все колбэки каталога завёрнуты в `useCallback`: без
  стабильных пропсов `memo` на панели не даёт ничего. Идентичность `Fighter` меняется только
  при рефетче `['fighters']` — ровно тогда, когда карточка и должна перерисоваться.
  Остальное намеренно не мемоизировано: `filtered` уже под `useMemo`, а nuqs кэширует
  распарсенные значения (`filters.types`/`filters.ranges` держат ссылку, пока не менялась
  query-строка), поэтому фильтрация 1300 записей на скролле не пересчитывается и без
  дополнительных обёрток. Компоненты арены (`BattleArena`, `BattleLineup`) ререндерятся на
  каждый такт плейбека — это и есть их работа, мемо там было бы вредным.
- **Обрыв сети: приложение продолжает работать, и оно об этом говорит.** Раунд-трипов за
  данными нет вообще — ростер вшит в бандл на этапе сборки, пользовательские правки лежат в
  IndexedDB, — поэтому каталог, поиск, редактирование, сборка составов и бой работают офлайн
  целиком. По сети приходит единственное: спрайты и крики с PokeAPI-репозитория. Без
  объяснения это читается как «сломалось приложение», поэтому `useOnlineStatus`
  (`useSyncExternalStore` по `online`/`offline`, серверный снимок — `true`, чтобы полоса не
  появлялась в SSR и не гасилась гидрацией) и полоса `OfflineNotice` в хедере говорят, что
  пропали именно картинки. Полоса рендерится **под** строкой хедера, а не внутри: её высота —
  переменная `--app-header-h`, к которой привязаны sticky-отступы каталога и досье бойца, и
  рост строки сдвинул бы их все.
- **`networkMode: 'always'` в дефолтах `QueryClient` — обязателен, иначе обещание «работает
  офлайн» ложное.** По умолчанию TanStack Query считает, что `queryFn` ходит в сеть, и при
  `navigator.onLine === false` переводит запрос в `fetchStatus: 'paused'` — он просто не
  выполняется. Здесь же ни один `queryFn` сеть не трогает: это чтение IndexedDB и импортированного
  JSON. Без этой строки каталог в офлайне показал бы пустое состояние вместо ростера, который
  физически лежит на диске (пауза — это `pending`, но не `fetching`, поэтому даже скелетон бы не
  отрисовался). Рядом выставлены `retry: 1` (локальное чтение либо работает, либо сломано
  по-настоящему — три ретрая с backoff только оттянули бы показ ошибки на секунды) и
  `refetchOnWindowFocus: false` (перечитывать локальный снимок на каждый фокус вкладки незачем,
  а подписчиков он ре-рендерит).
- **Skeleton/error/empty/список живут в одной колонке обычного потока.** Требование "loading
  без layout shift" теперь выполняется не фиксированной высотой блока, а тем, что скелетон —
  это тот же грид с той же высотой карточки (`h-[336px]`), что и загруженный список: переход
  "загрузка → готово" заменяет плитки карточками той же геометрии. Догрузка следующей
  страницы тоже не дёргает страницу — sentinel сам является рядом скелетонов, который
  вытесняется вниз новыми карточками.
- **`buildOverridePayload` диффит отправленную форму против `getBaseFighterById`
  (снимок без override), а не против того, с чем форма открылась.** Если боец уже был
  отредактирован раньше и пользователь меняет только одно поле сейчас, диф против "текущего
  смерженного состояния" не увидел бы разницу в остальных полях — а `db.overrides.put()`
  полностью заменяет запись, значит старые правки в невидимых для дифа полях тихо потерялись
  бы. Диф против истинного base эту проблему убирает: в override всегда попадают все поля,
  которые когда-либо отличались от оригинала, независимо от того, в этом сохранении их
  трогали или нет. Покрыто тестом отдельно (`editFighter.test.ts`) — без него баг незаметен
  в UI при одном редактировании и проявляется только на втором.
- **Форма редактирует все 10 статов реестра (`entities/stat`), не только шесть боевых.**
  `height`/`weight`/`captureRate`/`baseHappiness` уже участвуют в сравнении команд наравне с
  боевыми статами (см. решение про `statRegistry` выше) — показывать их только в фильтрах, но
  не давать редактировать, было бы непоследовательно.
- **`entities/fighter/ui` не может знать о `entities/stat`.** Оба — срезы слоя entities,
  кросс-импорт между ними запрещён правилами FSD из этого проекта. Поэтому карточка каталога
  (`FighterCard`) и её "СУММА" считают только по локально захардкоженным
  `BATTLE_STAT_KEYS` (`entities/fighter/model/battleStats.ts`) — шести боевым статам, а не по
  всему реестру. Компонент, которому нужны все 10 статов (форма редактирования, диапазонные
  фильтры), живёт в `features`/`widgets`, куда обе entities-срезы можно импортировать свободно.
- **Составы — по 5 бойцов на команду, не по 6, как в дизайн-брифе.** Прямое решение по
  запросу заказчика: `features/team-builder/model/teamSlots.ts` фиксирует `TEAM_SIZE = 5`.
  Экраны дизайн-пакета (герой-драфт, `#team`) везде считают 6/6 — реализация сознательно не
  подгонялась под макет, задание на этот счёт уточнено отдельно. Вернуть 6 — вопрос одной
  константы, слоты (`team-a`/`team-b`) и правила (нельзя быть в обеих командах, нельзя
  дублировать) от размера не зависят.
- **Параметр сравнения выбирает пользователь, а «сумма всех характеристик» — один из
  вариантов выбора (и вариант по умолчанию).** ТЗ требует в бою выбор параметра сравнения
  (п. 7) и возможность сравнивать команды по кастомному параметру «наравне с базовыми»
  (п. 5). Отдельно был прямой запрос «автоматом определять, кто сильнее, учитывая все
  характеристики». Эти два требования не противоречат друг другу, если авто-режим —
  это пункт в списке параметров, а не единственное правило: селектор
  (`features/battle-run/ui/ComparisonStatSelect.tsx`) показывает «Все характеристики»
  (псевдо-id `TOTAL_STAT_ID`), десять базовых статов и все кастомные — одним рядом,
  кастомные отличаются только точкой.

  Доменный слой знает об этом ровно один аргумент: `determineWinner(teamA, teamB, statId)`.
  Всё сведение «id параметра → число у бойца» лежит в
  `entities/battle/model/statScore.ts`: `TOTAL_STAT_ID` уходит в `totalStatScore` (сумма
  всего, что лежит в `fighter.stats` — шесть боевых статов,
  `height`/`weight`/`captureRate`/`baseHappiness` и назначенные кастомные), любой другой id —
  это `fighter.stats[statId] ?? 0`. Ветки «базовый или кастомный» здесь нет и не нужно:
  `mergeFighter` к этому моменту уже сложил и то и другое в один `stats`, поэтому кастомный
  параметр сравнивается тем же кодом, что и базовый — это и есть «наравне».

  Боец без значения параметра получает 0 и проигрывает слот, а не выпадает из состава:
  он всё равно стоит в своём слоте, и проиграть — честный исход отсутствия значения. Если
  значения нет ни у кого, все раунды — ничьи, и разбор говорит об этом прямым текстом, а не
  оставляет пользователя разбираться с таблицей нулей.

  Победа в бою — по числу выигранных раундов, как и в брифе; сумма параметра по составу
  показана в подвале разбора, но ничего не решает. Когда эти два числа расходятся
  (у проигравшего сумма выше — один очень сильный боец не перекрывает четыре проигранных
  пары), панель это отдельно оговаривает, чтобы подвал не читался как противоречие вердикту.

  Выбранный параметр живёт в query-строке (`?stat=...`), как и фильтры каталога: переживает
  reload и шарится ссылкой. Результат боя при смене параметра снимается — не эффектом, а
  тем, что `BattleOutcome` несёт в себе `statId`, на котором он посчитан, и читается только
  при совпадении с выбранным (`useBattleRun`). Так на экране физически не может остаться
  вердикт, не соответствующий селектору.

- **«Разбор, почему победил» — отдельная чистая функция, а не текст в компоненте.**
  `entities/battle/model/battleExplanation.ts` (`explainBattle`) — проекция уже посчитанного
  `BattleOutcome`: раунды с обоими числами и разрывом, суммы по сторонам и «решающий раунд»
  (самый крупный разрыв среди выигранных победителем; при равных разрывах — более ранний,
  чтобы один и тот же бой всегда объяснялся одинаково). Она ничего не пересчитывает, поэтому
  таблица не может разойтись с вердиктом над ней — тест на это есть. Функция принципиально
  не знает подписей статов (`entities/battle` не импортирует `entities/stat`, см. правило про
  кросс-импорты entities) — работает с `statId`, а человеческое название подставляет UI из
  реестра. Рисует это `widgets/battle-result/ui/BattleBreakdown.tsx`, и рисует только после
  анимации: таблица выдаёт результат каждого раунда, и показать её во время боя — заспойлерить
  то, что она объясняет.
- **Список страниц приложения — данные (`shared/config/navigation.ts`), а не разметка хедера.**
  Добавление защищённого маршрута — это строка в `APP_NAV`, а не правка JSX. Там же живёт
  `isNavItemActive` с полем `ownsPrefixes`: у `/fighter/[id]` нет своей пилюли в навигации, и
  без этого на странице досье бойца хедер оставался бы без активного пункта — вместо этого
  подсвечивается "Покедекс", из которого туда и попадают. Логика чистая и покрыта тестом
  (`navigation.test.ts`), в частности на то, что `/battle-history` не активирует `/battle`
  по совпадению префикса имени.
- **`AppHeader` — серверный компонент, интерактив вынесен в два клиентских (`AppNav`,
  `UserMenu`).** Сессию читает `auth()` на сервере (в браузер не уезжает ни сам вызов, ни
  `signOut`), а `usePathname` и дропдаун требуют клиента. Выход оформлен как server action
  (`features/auth-logout`) внутри настоящего `<form>`, а не `onClick`: `signOut` должен
  выставить куки и сделать redirect, что возможно только на сервере, и в таком виде кнопка
  работает даже до гидратации.
- **`MenuLabel` в `shared/ui/menu.tsx` — обычный `<div>`, а не `Menu.GroupLabel` из Base UI.**
  Не стилистическое предпочтение: `Menu.GroupLabel` читает `MenuGroupContext` и падает с
  `MenuGroupContext is missing`, если не обёрнут в `<Menu.Group>` — что и произошло при первом
  прогоне (тайпчек и сборка этого не видят, поймалось только запуском приложения в браузере).
  Оборачивать в группу заголовок, который подписывает всё меню, а не одну группу пунктов внутри
  него, — неверная семантика, поэтому заголовок стал обычным элементом, а `MenuGroupLabel`
  оставлен отдельно для меню, где группы реально есть.
- **Русские подписи типов (`typeLabel` в `entities/fighter/model/tone.ts`).** Интерфейс целиком
  русский, и сырые PokeAPI-идентификаторы (`fighting`, `flying`) протекали в чипы фильтров и
  карточки. Значением везде остаётся английский id — он же ключ, он же значение query-параметра
  `?types=fire`; переводится только то, что видит пользователь.
- **Карточка бойца без цветной подложки под спрайтом.** Прямое решение по запросу заказчика:
  раньше арт лежал на плашке в цвете стихии (`TONE_BG`), и на сетке из 48+ карточек это читалось
  как пёстрое лоскутное одеяло из трёх акцентов. Теперь плашка нейтральная (`bg-black/45`), а
  принадлежность к стихии несут чипы типов и цвет значения "СУММА" — акцент остался
  информативным, но перестал быть фоном.
- **Слайдер диапазона красит заполнение акцентом только когда диапазон реально сужен.**
  Нетронутый фильтр занимает всю ширину границ, поэтому единый красный fill на всех десяти
  слайдерах читался как "включены все фильтры". Неактивные теперь серые (`white/20`), активный —
  `brand-red`; проверено на computed styles, а не на глаз.
- **Панель фильтров — собственный скролл-контейнер, а не просто `sticky`.** С раскрытыми
  диапазонами панель выше вьюпорта (1181px контента против ~727px доступных), и пока она была
  только `sticky`, добраться до нижних фильтров можно было единственным способом — прокрутив
  всю страницу, то есть утащив за собой сетку карточек. Теперь у панели `max-height` от высоты
  вьюпорта (`--app-header-h` в `globals.css` — единый источник высоты хедера, вместо
  захардкоженного пикселя в каждом месте) и внутренний `overflow-y`, плюс `overscroll-contain`,
  чтобы докрутившийся до конца внутренний скролл не переходил на страницу. Проверено колесом
  мыши в браузере: над панелью `railScrollTop` растёт, `window.scrollY` не меняется; над сеткой
  наоборот — страница едет, панель остаётся приколотой.
- **`items-start` на гриде "фильтры + сетка" обязателен.** Без него панель растягивается
  (`align-items: stretch`) на всю высоту ряда и рендерится как почти пустая коробка до самого
  `max-height`. Со `items-start` панель по высоте контента (591px в свёрнутом виде вместо 780px
  пустоты), и `sticky` при этом не ломается: sticky-грид-элемент позиционируется внутри своей
  *grid area*, а она равна высоте ряда, заданной высокой колонкой с карточками, а не высоте
  самого элемента.
- **Числовые поля диапазона коммитят значение на blur/Enter, а не на каждое нажатие клавиши.**
  Не стилистика, а исправленный баг: при коммите на каждый keystroke ввод "120" превращался в
  200. Промежуточное "1" клампилось до минимума, контролируемый инпут перерисовывался этим
  клампленным значением, и следующие цифры дописывались к нему ("5" → "5120" → кламп до 200).
  Теперь набранное живёт в локальном черновике (виден ровно как набран, без кламп), а кламп к
  границам и ко второму концу диапазона происходит один раз при коммите. Проверено в браузере:
  "120" → `?ranges=speed:120:200` (89 бойцов), "9999" → кламп до реального максимума 200.
- **Чипы стихий — сетка 2×9, а не заворачивающиеся пилюли.** 18 названий разной длины при
  `flex-wrap` дают рваный правый край; ячейки одинаковой ширины читаются как осознанный список.
  Заодно снята насыщенность: принадлежность к стихии теперь несёт маленькая точка в цвете тона,
  а не залитая цветом пилюля — 18 цветных блоков рядом с сеткой карточек перетягивали внимание
  на себя.
- **Сетка каталога ограничена 4 колонками.** Контейнер упирается в 1560px, поэтому пятая
  колонка только сжимает карточку до ~230px и ломает блок статов; при четырёх — ~278px, и
  карточка перестаёт выглядеть тесной. Ширина рейла фильтров (288px) подобрана под самую длинную
  подпись диапазона ("СЛОЖНОСТЬ ПОИМКИ") плюс два числовых поля.

## Что не сделано и почему

На момент последнего коммита сделаны: скаффолд + FSD-границы, датасет PokeAPI (build-time
скрипт, расширенный до высоты/веса/сложности поимки/счастья/легендарности/шайни-спрайта/крика),
доменная модель бойца и merge-слой с тестами, `entities/stat` с базовым реестром статов,
моканная авторизация с proxy-guard, лендинг, настоящий рабочий `/catalog`
(`widgets/catalog-browser` — подстроковый поиск, фильтры, автопагинация,
loading/empty/error), `/fighter/[id]`
(`widgets/fighter-detail` + `features/fighter-edit` — форма на TanStack Form + Arktype с
сохранением/сбросом через Dexie и тестами на диф override), `features/custom-stat-create`
(создание пользовательского параметра и присвоение значения бойцу, реестр `entities/stat`
подхватывает его как `source: 'custom'` — в том числе в диапазонных фильтрах каталога),
`features/team-builder` (сборка двух команд по 5 в Dexie — таблица `teams`, см. "Принятые
решения" про отличие от 6 в брифе) и `/battle`: выбор параметра сравнения (базовый,
кастомный или сумма всех), `entities/battle` — `determineWinner.ts`, `statScore.ts`,
`totalStatScore.ts`, `battleExplanation.ts`, `duelScript.ts`, все с юнит-тестами;
`features/battle-run` (проверка готовности составов, селектор параметра, запуск и плейбек боя),
`widgets/battle-result` (арена с анимацией, вердикт и панель разбора по раундам).

Тесты: `bun run test` → 19 файлов, 132 теста. Обязательное по ТЗ покрытие — логика определения
победителя — лежит в `entities/battle/model/*.test.ts`: чистота (никакого времени, рандома и
I/O в пути), детерминированность (один и тот же бой всегда даёт один и тот же результат),
поведение на неполных составах, сравнение по одному стату против суммы, кастомный параметр
наравне с базовым, и то, что анимация арены (`duelScript`) не может закончиться победой
стороны, проигравшей по счёту.

Ниже — то, что специфицировано, но не реализовано:

- **Поиск не видит пользовательские правки имени и описания.** Индекс строится по неизменяемому
  снимку PokeAPI. Если переименовать Pikachu в «Громовержца», по новому имени он не найдётся, а
  по старому — найдётся. Причина: индекс собирается один раз на уровне модуля, и учёт правок
  означал бы либо пересборку 1300 документов после каждого сохранения, либо инкрементальный
  `replace` с изменяемым состоянием модуля, которым управляет React. Правильное решение —
  второе, оно небольшое, но требует аккуратности с конкурентным рендерингом. Зафиксировано
  честно вместо того, чтобы сделать наспех, — но **из всего списка это первое, что стоит
  доделать**: ТЗ просит искать по имени, а имя редактируемое.
- **Компонентных и e2e-тестов нет.** ТЗ прямо говорит, что покрытие всего не оценивается, а
  обязательный участок (определение победителя) покрыт юнитами. Компонентные на состояния
  каталога и e2e на «вход → драфт → бой» — следующий шаг, но не в рамках 8–10 часов.
- **Производительность не измерена инструментами.** Решения по мемоизации, пагинации и
  `useDeferredValue` обоснованы рассуждением и замером самого поиска, но React Profiler и
  Lighthouse на полном датасете я не гонял. Честная формулировка — не «оптимизировано», а «нет
  очевидных источников лишней работы».
- **История боёв** — в ТЗ это **опциональный** пункт, а в дизайн-брифе описан экран
  `#history` с таблицей (`battles`: `id`, `date`, `teamA`, `teamB`, `stat`, `winsA`, `winsB`)
  и экспортом JSON. Не делал сознательно: опциональное — только если не в ущерб обязательному,
  а обязательного (выбор параметра сравнения, разбор, подстроковый поиск) на момент ревизии
  хватало. Заготовки «на будущее» под это в коде нет — пустой опциональный блок честнее
  недоделанной таблицы.
- `eslint-plugin-boundaries` (или steiger) с правилами FSD как lint-ошибка в CI — пока границы
  слоёв соблюдаются вручную по договорённости, автоматической проверки нет.
- Опциональная часть — не выбиралась, приоритет обязательной части.
- **Спрайты офлайн** — при обрыве сети картинки просто не приходят (хедер об этом сообщает,
  см. "Принятые решения"), но `onError`-заглушки на месте спрайта нет. Это 11 мест с `next/image`
  и разной вёрсткой в каждом; выносить их в общий `FighterSprite` — отдельная задача с риском
  для визуального слоя, и на «поведение при обрыве сети» она влияет меньше, чем сама полоса.
- Деплой на Vercel — репозиторий и коммиты локальные, задеплоено будет на финальном этапе.

## Что дальше в продакшене

Если бы это был продукт, а не тестовое, — в таком порядке:

1. **Бэкенд и синхронизация.** Сейчас правки живут в IndexedDB одного браузера: другой
   компьютер — другие данные, очистка кэша — потеря всего. Первым делом нужен API с
   user-scoped хранилищем, а Dexie становится офлайн-кэшем и очередью отложенных записей.
   Конфликты решать по `updatedAt` **на уровне поля** (правки разных характеристик одного
   бойца независимы), а не заменой строки целиком — иначе воспроизведём в распределённом виде
   ровно тот баг, который уже ловили в `buildOverridePayload`.
2. **Настоящая авторизация.** Credentials-мок меняется на реальный провайдер: refresh-токены,
   роли и права (кто правит общий каталог, а кто только свою копию). Список пользователей из
   `shared/config/users.ts` исчезает вместе с моком.
3. **Обновление датасета без передеплоя.** 937 КБ JSON сейчас лежат в бандле. В проде — отдельный
   версионированный ресурс с ETag и фоновой дозагрузкой, чтобы обновление данных не требовало
   пересборки приложения, а пользователь не платил за него первым рендером.
4. **Миграции и отказы хранилища.** Схема Dexie — `version(1)`. Нужны политика миграций и явная
   обработка отказов: приватный режим, `QuotaExceededError`, заблокированное обновление версии
   в соседней вкладке. Сейчас такая ошибка станет обычным error-состоянием запроса, без
   объяснения пользователю, что именно произошло.
5. **CI и автоматические границы.** `tsc` + `eslint` + `vitest` на каждый PR и
   `eslint-plugin-boundaries` с правилами FSD как ошибка сборки — чтобы архитектура держалась
   линтом, а не договорённостью и ревью.
6. **Тесты выше юнитов.** Компонентные на состояния (loading/empty/error каталога, диф формы) и
   e2e на сквозной сценарий «вход → драфт → бой». Плюс тест на регресс merge-слоя при изменении
   схемы датасета — он сейчас самое хрупкое место при обновлении данных.
7. **Замеры вместо рассуждений.** React Profiler на скролле каталога, Lighthouse на лендинге,
   бюджет бандла в CI. Если датасет вырастет на порядок — индекс поиска в Web Worker и его
   персист в IndexedDB, чтобы не строить его при каждой загрузке страницы.
8. **Наблюдаемость.** Sentry с отдельной группировкой ошибок Dexie: именно там ломается то,
   что невозможно воспроизвести локально — чужой браузер, чужая квота, приватный режим.
9. **Доступность выше базовой.** Клавиатурная навигация по карусели драфта, управление фокусом
   при открытии панелей, проверка контраста акцентов на тёмном фоне.
